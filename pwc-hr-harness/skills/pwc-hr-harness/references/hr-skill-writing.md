# HR Skill 작성법

> 기본 팀 Skill 을 고치거나 새 HR Skill 을 만들 때 읽는다. 원칙은 revfactory/harness 스킬 작성 가이드 (적극적 description · Why 설명 · Lean · 일반화 · 반복 코드 번들)에 HR 규칙을 얹은 것이다.

## 1. 「잘 된 프롬프트 = 우리 회사의 인력계획 규칙」

Day 2 실습에서 잘 된 지시문은 Skill 이 된다. Skill 은 회사의 판단 규칙을 담은 문서다: 무엇을 입력으로 받고, 어떤 순서로, 어떤 기준으로 판단하고, 어디서 멈추고, 무엇을 하지 않는가. 사람이 바뀌어도, 다른 사람이 돌려도 같은 결과가 나와야 좋은 Skill 이다.

## 2. SKILL.md 틀 (표준 단계 Skill 공통)

```markdown
---
name: <소문자-하이픈>
description: "<하는 일 한 문장>. <언제 쓰는가 · 사람이 실제로 할 말 4~6개 「…」>. <하지 않는 일 · 비슷하지만 다른 Skill>"
---
# <이름> · <단계>
법전 근거: <개념 (D1-NN)> · …
## 절차          (스크립트 명령 · 담당이 판단하는 칸 · 멈추는 자리)
## 계산식        (스크립트가 하는 것 · 법전 공식 그대로)
## 입력 계약     (입력 | 필요한 것 | 없을 때)
## 판단 규칙     (「~한다 / ~하지 않는다」 · 출처)
## 금지
## 이음매        (다음 단계 입력 계약과 같아야 하는 열 이름)
## 끝낼 때       (리드에게 돌려줄 것 · 이전 결과가 있을 때)
```

- **description 은 적극적으로** 쓴다. Claude 는 트리거를 보수적으로 판단하므로, 하는 일 + 실제 요청 문장 + 하지 않는 일을 함께 적는다. 다시 실행 · 일부만 다시 · 가정 바꿔서 같은 후속 표현도 넣는다
- 본문 500줄 이내. 길어지면 `references/` 로 나누고 「언제 읽으라」를 남긴다
- 명령형으로 쓰고, 규칙에는 이유를 붙인다 (「빈칸을 0 으로 읽지 않는다 · 공급이 과대해진다」)

## 3. 판단과 계산을 나눈다

| 칸 | 누가 | 어디에 |
|---|---|---|
| 계산 (FTE · 퇴직률 · 회귀 · Gap) | 스크립트 | `scripts/*.py` (같은 입력 = 같은 숫자) |
| 판단 값 (동인 선정 · 보정 계수 · 시나리오 · 가정 배수) | 담당이 초안 · 사람이 승인 | 파라미터 파일 (`②_수요파라미터.md` · `③_공급가정.md`) |
| 판단 문장 (사업전략 해석 · 대안 · 요약) | 담당 · 리드 | 결과 md 의 담당 칸 |

- 스크립트는 판단하지 않는다. 판단이 필요하면 멈추거나 「제안」으로만 낸다 (예: 상관 1위가 원칙 위반이면 표시만 하고 다음 후보를 제안)
- 파라미터 파일의 숫자 칸에는 근거 칸을 짝으로 둔다 (파일 1 절 · 문장). 근거 없는 숫자는 검증 담당이 「출처」 미해결로 잡는다

## 4. 멈춤을 코드로

기본 엔진 `hrlib.py` 를 쓴다.

```python
import hrlib as H
H.require_cp(ws, 'CP2', '②_수요파라미터.md', '② 수요 계산')        # 앞 CP 승인 없으면 멈춤
raise H.Stop('예외', 'FTE범위', '무엇을 정해야 하는가', [근거…], [선택지…])   # 데이터 이상
H.allowed(args, 'FTE범위')   # 사람이 고른 예외 처리 (--allow FTE범위=진행)
H.approval_block('CP4', '인사기획팀장 + 해당 본부장')              # 승인 표 (config.json approvers 로 바꿈)
H.replace_auto(text, 'gap', block)                                  # 스크립트 칸만 다시 씀
```

- 멈춤은 종료 코드 3 + `outputs/<회사>/_멈춤.md` (4요소). 리드는 그 파일을 그대로 보여 준다
- 빈칸은 `None` 그대로 둔다. 숫자로 읽을 때 `H.num()` 은 빈칸에 에러를 낸다 (0 으로 바꾸지 않음)
- 기본 표는 `H.load(ws, '<표 키>')` 로 읽는다 (열 대응표 적용 · 집계 행 제외 · 행마다 `_ref` 출처)

## 5. 데이터 사전 공통 규칙 (모든 Skill 판단 규칙의 바닥)

1. 단위 칸이 비면 계산을 멈춘다 2. 기준일이 다른 값은 한 표로 합치지 않는다 3. 집계 행은 데이터 행이 아니다 4. 빈칸과 0 은 다르다 5. 표 머리 위 안내문은 데이터가 아니다 6. 숫자마다 출처 7. RPU 코드가 이음매다

## 6. Skill 을 바꿨을 때 (자사 버전 · 진화)

1. 바꾼 이유를 CLAUDE.md 변경 이력에 한 행
2. `customize.py lock` (잠긴 규칙이 그대로인지)
3. `customize.py regress --co K-co` (K-Co. 숫자가 그대로인지 · 다르면 의도한 변화인지 사람 확인)
4. 다른 사람 Skill 로 같은 데이터를 돌려 같은 결과가 나오는지 (Day 2 교환 실행)
5. 트리거 확인: 해야 할 요청 3개 · 하면 안 되는 비슷한 요청 3개 (예: 「공급 예측」은 step3 · 「퇴직자 명단」은 어떤 Skill 도 하면 안 됨)

## 7. 좋은 Skill · 나쁜 Skill

| 나쁜 Skill | 좋은 Skill |
|---|---|
| 「수요를 예측해 줘」 한 줄 | 입력 계약 · 절차 · 판단 규칙 · 멈춤 · 금지가 있음 |
| K-Co. 열 이름에 묶임 | 열 대응표로 기본 열을 읽음 (자사 데이터에 그대로) |
| 숫자를 그때그때 말로 계산 | 스크립트로 계산 (재실행 일관성) |
| 「적절히 판단」 | 판단 기준과 출처 (법전 장 번호 · 회사 기준) |
| 끝까지 혼자 감 | 정해진 CP 와 데이터 이상에서 멈추고 4요소로 묻는다 |
